# E2M 角色页面与信息架构事实基线（2026-07-21）

> **历史文档（2026-07-21 快照）。** 本文所述事实已被 2026-08-04 平台商业化批次全面取代：支付下单与回调、钱包充值、兑换码、基准价目表定价、用户级限流、统一设置模块均已实现（默认由 `E2M_ENABLE_PAYMENTS` 关闭），控制台信息架构也已重构为「平台管理 / 通用功能」两区。本文**不再对任何其他文档具有优先权**；现状以 [current-state.md](current-state.md) 与 [platform-commerce-execution-plan.md](platform-commerce-execution-plan.md) 为准。

本文基于当前工作区代码、前端路由、菜单、后端授权以及本地运行界面的只读走查，记录“当前真实可见页面”和“页面当前真正承载的业务”。（原文此处声明本文在页面入口、角色可见性、接入向导上优先，该声明已于 2026-08-04 撤销。）

## 1. 业务目标与评估口径

本次评估以当前已对齐的目标为准：

1. 面向下游 `client` 提供平台统一采购、交付和运维的上游能力；用户只选择有限、可解释的智能路由偏好。
2. Connector 旁路连接用户网关，平台自动完成共享上游的 Key 分配、本地 Binding 安装与证明、网关账号发布、健康观测、故障摘除和渐进恢复。
3. 未来资金方向是用户先充值平台余额，再按可信账务规则消费；需要解决上游成本对账、预授权/冻结、扣款、退款和防透支。当前代码尚未形成该资金闭环。
4. `supplier` 应最终形成“资源登记、审核与质检、分配、实际履约、消耗、结算与收益”的供应链，但当前只完成资源登记与分配台账骨架。

页面评级：

- **核心**：直接承载上述主业务，应该保留并重点补强。
- **支撑**：有治理或配置价值，但不一定应占一级入口。
- **旧链路**：主要服务用户自有账号或早期手动运维，不是平台托管主路径。
- **骨架**：界面或数据模型存在，但业务闭环尚未成立，不应对外暗示已经可用。

## 2. 权限模型的重要事实

- 侧栏和 `RequireRole` 按右上角 `activeRole` 裁剪页面。
- `activeRole` 只是前端视角；API Token 不携带该字段，后端始终按账号拥有的全部角色鉴权。因此多业务角色账号切换视角时，页面隐藏不等于后端能力消失。
- `admin` 不能与业务角色组合；`client + supplier` 可以组合。
- 下表中的 `菜单` 表示侧栏入口，`直达` 表示无侧栏但路由可进入，`—` 表示该前端角色会被路由守卫退回首页。

## 4. Client 页面逐项评估

### 4.1 概览：核心，但业务指标选错

当前展示实例数、在线 Connector、实例状态分布和最近活动。它应该回答“我的服务能不能用、接入卡在哪里、余额还能用多久、最近发生了什么”，但目前实例常见 `unknown`，且活动流容易被重复自动重试污染。

建议保留并改成“服务总览”：展示接入进度、已交付/可调度线路、当前服务状态、SLA、开放事故和下一步操作。资金闭环完成后再加入可用余额与预计可用时长。

### 4.2 实例管理：核心，但操作过载

它是用户登记 Sub2API/NewAPI/CPA 托管对象的入口，业务必要。当前又能生成 Connector 安装引导、绑定 Connector、编辑监控策略，和 Connector 页面重复；接入后仍允许修改网关类型也有风险。

建议把它定位为“接入实例与服务范围”，实例创建后锁定或受控迁移网关类型；Connector 安装与诊断集中到接入流程或实例详情。

### 4.3 连接器：核心设施，宜降为接入/诊断页

真实自动交付依赖 Connector 在线、网关测试通过、心跳新鲜、Binding 加密与证明能力。页面本身有价值，但 Token 轮换、任务队列等工程细节不应成为普通用户日常主任务。

建议在主路径只呈现“已连接/需处理/如何修复”，高级任务历史放进抽屉或诊断区；删除与实例页重复的安装入口。

### 4.4 我的 API Key：核心交付证明，但产品定位冲突

这是普通用户确认“平台已经给我分配资源，并已安全安装到本地 Connector”的权威入口。当前还允许密码验证后 60 秒查看、复制明文。

若未来目标是平台统一余额、可信计量和防止账单溢出，允许用户拿到可直连上游的 Key 会形成绕开 Connector/网关计量的旁路。建议将页面改名为“已交付资源”，默认只展示来源、版本、分配状态、Binding 证明和发布回执；是否继续允许明文导出需要作为商业与安全决策单独确认。

### 4.5 账号健康（client）：当前最契合产品目标

client 在这里看到匿名化的托管容量、可用性、五分钟 SLA、事故、切换记录，并能选择智能自动、价格优先、速度优先、成功率优先。它正好对应“平台管安全底线，用户选有限路由意图”。

需要补强：按实例/服务范围筛选；展示偏好的覆盖关系和生效时间；解释“价格优先”目前是成本提示而非用户结算价；加入接入阻塞原因和明确下一步。页面名建议改为“服务质量与路由”，避免让用户误以为能看到平台账号明细。

### 4.6 告警通知：必要支撑

运维通知对托管服务必要，但当前缺测试发送、实际投递成功率/最后错误；`quiet_window` 和 `escalation_after` 目前主要是存储与展示，不能对外暗示已有完整静默和升级执行。

建议保留为“通知设置”，把 client 的通知凭证在此就地维护，不再要求用户理解通用凭证库。

### 4.7 审计日志：必要治理，但不适合作为故障排查主界面

审计是不可替代的最终操作事实源。当前技术 action、原始 ID、JSON 细节和有限筛选对普通用户不友好；接入失败只能靠翻审计也是明显 UX 缺口。

建议保留但降到“高级/安全”，增加按实例、业务事件、结果和时间筛选及详情跳转。接入失败应在概览或接入进度页直接解释。

### 4.8 上游账号：旧链路，应明确降级

该页会过滤 RoutePlan 管理的平台账号，只服务用户自有账号的手工启停、一键切换和批量审批。它不是平台托管 Key 的交付或验收页。

建议改名“自有上游账号（高级）”，从实例详情的高级入口进入；若产品不再支持用户自带上游，则可整体下线。

### 4.9 待办审批：当前名称和一级入口过大

当前引擎只支持 `batch_set_schedulable`，而且明确拒绝操作平台 RoutePlan 托管账号；它没有承接自动切换决策。普通用户可以发起本人自有账号批量启停，页面却叫通用“待办审批”。

建议合并到“自有上游账号”的操作记录；等未来真的有充值风控、预算变更或高风险路由变更审批，再建设统一待办中心。

### 4.10 凭证管理：通用模型合理，client 一级页面不合理

client 主业务通常只需要通知 Webhook；平台托管交付 Key 不由 client 在这里填写，client 的 upstream/proxy 凭证当前也没有清晰的主链路消费。

建议从 client 主导航移除，通知凭证并入通知设置；只有开启“自有上游/自有代理”的高级模式时才显示相关凭证。

### 4.11 账单与费用：旧计费估算，不是未来钱包

当前固定为每实例每月 199 元，加每次已接受账号处置 1 元，请求页面时实时重算；没有账单固化、到期、结清、冲销、优惠、税务或支付订单关联。它与已经确认的“用户购买账户余额”方向不同。

建议立即改名“费用估算（旧模型）”或用 feature flag 隐藏。未来应由“余额与账务”取代，至少包含充值、可用/冻结余额、消费流水、价格版本、对账差异、退款/冲正和余额门禁。

### 4.12 接入向导：P0 重做，当前不能作为事实入口

当前页面把任意凭证当必需、把 Connector 写成可选、只要 Connector 未吊销就判完成、用 RoutePlan 数量判发布，而 `client` 无权读取 RoutePlan API；`allDone` 甚至不要求 Connector 成功。因此它会给用户错误动作和错误完成状态。

真实流程是 Connector 就绪后后台默认每 15 秒自动创建计划、分配 Key、安装 Binding、发布和验证，用户无需点击发布。建议删除现页面，重做为后端工作流驱动的“自动接入进度”：实例 → Connector 就绪 → 资源分配 → 本地安装证明 → 网关发布 → 服务可用，并显示阻塞原因、下次重试和“联系平台/重试”动作。

## 5. Admin 页面逐项评估

### 5.1 平台概览：核心，但当前过于基础

仅有用户、实例、供给、在线 Connector 和活动，不能回答平台值班最重要的问题。建议展示接入成功率与失败队列、可交付库存、开放事故、观测覆盖、用户服务受影响面，以及未来的资金风险与账实差异。

### 5.2 运维中心：核心主驾驶舱，应优先补操作闭环

它聚合来源健康矩阵、自动接入进度、事故恢复和网关回执，是当前最接近真实运维任务的 admin 页面。但几乎只读，缺用户/实例/池筛选、事故钻取、立即重试、人工恢复和跳转到对应 Channel、Plan、Binding、Connector。

建议将它确定为管理员主工作台，并补齐从发现到修复的闭环。

### 5.3 实例管理与连接器：核心客户接入能力

admin 需要跨用户处理接入和 Connector 故障，但两个页面重复安装引导，Connector 任务时间线又与运维中心重复。实例创建表单还会列出所有用户，而后端只允许 enabled client。

建议合并为“客户接入”，按客户/实例组织，内含 Connector、自动接入工作流和修复动作；表单按合法角色预过滤。

### 5.4 上游编排：核心，但单页承担过多领域

一个页面同时维护 Pool、Channel、RoutePlan、跨计划策略、自动切换状态、健康快照、决策、发布历史和 Binding，技术字段密集。启用 active Pool 会使其自动覆盖所有 eligible client 实例，当前 UI 对影响面提示不足。

建议按任务拆为：

1. **上游资源目录**：来源、Channel、Pool、成本与容量。
2. **路由与安全策略**：平台质量底线、用户偏好模板、覆盖优先级。
3. **发布与部署**：计划、预检、发布、回滚、Binding 与执行历史。

### 5.5 Key 交付配置：核心准备度，但应与 Channel 统一

平台渠道变成可交付状态必须有 Key 库存、版本和证明，因此页面必要。当前与 Channel 分离，聚合 proof 容易被误解为所有实例均就绪。

建议成为 Channel 详情中的“交付库存与部署证明”，同时区分渠道级汇总和每实例权威回执。

### 5.6 admin 账号健康：与运维中心重复且概念混杂

admin 的 `/pool-health` 仍展示详细健康运维与旧账号级自动切换，而 client 同一路径看到完全不同产品页。它与运维中心、网关能力有大量重复。

建议取消 admin 一级入口：池/来源健康并入运维中心；旧自有账号健康放入实例详情。client 页面另用明确路径和名称，例如 `/service-quality`。

### 5.7 凭证管理：必要密管，但应按上下文拆分

admin 需要跨用户 Vault 治理，但“上游凭证”容易与平台 Delivery Key 混淆；表单列出所有用户和所有 kind，后端实际要求 notification 对应 client、upstream/proxy 对应 supplier。

建议按角色和用途过滤，或分别嵌入通知渠道、供应商、Channel 页面，独立页面只作为安全管理员的密管索引。

### 5.8 告警、审计、用户与权限：必要支撑

- 告警：补测试投递、最后成功/失败、重试与通道健康。
- 审计：作为统一事实源，其他页面少复制原始活动流，多提供上下文跳转。
- 用户与权限：保留；实例和凭证表单必须只显示合法角色用户。
- 系统认证设置：保留；和支付设置拆开，避免把成熟度不同的能力放在同一正式入口。

### 5.9 供给管理：骨架，尚未进入交付主链路

admin 分配 Offer 后只写 SupplyLedger；不会自动创建 Channel、DeliveryKey、Binding、RoutePlan，也不会触发该 Offer 的网关交付和 onboarding。当前“分配”只是纸面归属，不是实际履约。

建议在接通“审核/质检 → 可用库存 → 分配 → Channel/Key → 实际部署 → 消耗 → 供应商结算”前标记试验功能或隐藏，不能对外称已完成供应链。

### 5.10 收款订单与支付设置：骨架，应隐藏

当前没有用户 checkout、服务商下单、Webhook 验签去重、PAID/COMPLETED 推进、钱包入账、账单结清、退款执行或对账；管理端主要是查询详情和安全取消没有服务商交易号的本地 PENDING 订单。

建议 feature flag 隐藏。支付配置复杂度已经领先于资金账务能力，下一步应先定义内部钱包与可信账本，再接支付渠道。

### 5.11 网关能力：工程诊断，不应占平台管理一级入口

它是适配器兼容矩阵，和健康摘要有部分重复，业务管理员日常不会围绕它工作。建议移到“诊断/开发者工具”；若只允许 admin 看，后端 API 也应同步收紧。

### 5.12 待办审批：旧链路支撑

当前只审批自有账号的批量启停，未承接 RoutePlan 自动切换中的 proposed 决策。建议不再作为 admin 一级通用待办；并入客户实例高级运维，或扩展成真正统一任务中心后再恢复。

## 6. Supplier 页面逐项评估

### 6.1 概览：明显不足

当前只有供给数量和最近活动，不能回答供应商最关心的问题：多少可用库存、多少已分配、哪些履约异常、本期收入与待结算多少。

建议改为“供给经营看板”，前提是后端先建立真实履约和结算事实。

### 6.2 供给管理：有登记价值，但不是完整供应业务

可以登记 OAuth/API Key Offer、引用上游/代理凭证、额度和单价，编辑、撤销并查看分配台账；缺审核、质检、库存消耗、交付状态、SLA 反馈、收益和结算。

建议保留在试验区，直到 SupplyLedger 与 Channel/DeliveryKey/实际消耗及应付结算打通。

### 6.3 凭证管理：必要前置，但存在权限错配

supplier 需要 upstream/proxy Secret，页面却仍显示 notification 类型；后端会拒绝 supplier 写 notification。页面也不显示一个凭证被哪些 Offer 引用，轮换或删除的影响不透明。

建议改成“资源连接与凭证”，只展示合法类型，显示引用关系、轮换影响和连接测试。

### 6.4 审计日志：必要治理

应保留，但增加 Offer、Ledger、履约和结算维度筛选及详情跳转。目前 supplier 没有“分配与履约”“收益与结算”页面，这是角色信息架构的最大空缺。

## 7. 明确的前后端错配

1. `/onboarding` 允许 client 进入，却无条件调用 admin-only RoutePlan API，导致 client 403 且错误未被正确表达。
2. supplier 凭证 UI 可选 notification，后端只允许 upstream/proxy。
3. admin 创建实例的用户下拉含所有用户，后端目标必须是 enabled client。
4. admin 凭证表单未按目标角色过滤：notification 必须属于 client，upstream/proxy 必须属于 supplier。
5. `/capabilities` 前端仅 admin 可见，但读 API 实际只要求登录。
6. SupplyLedger 后端允许 client 查看本人作为 owner 的分配记录，前端没有对应页面；在供应链未闭环前不建议单纯把旧页面开放给 client，而应最终并入“已交付资源”。

## 8. 建议目标信息架构

### Client

1. **服务总览**：服务状态、接入进度、SLA、事故、余额与下一步。
2. **接入管理**：实例 + Connector + 后端驱动的自动接入工作流。
3. **服务质量与路由**：容量、SLA、事故、切换、四档路由偏好。
4. **已交付资源**：Key/来源版本、Binding 与发布证明，不默认暴露明文。
5. **通知设置**。
6. **余额与账务**：仅在钱包、计量、对账和防透支闭环后开放。
7. **高级与安全**：自有上游账号、审计；按产品开关显示。

### Admin

1. **平台总览**。
2. **运维中心**。
3. **客户接入**：客户、实例、Connector、自动接入工作流。
4. **上游资源目录**：来源、Channel、Pool、库存、成本、容量。
5. **路由与安全策略**。
6. **发布与部署**：计划、预检、Binding、发布、回滚。
7. **用户与权限**。
8. **通知与审计**。
9. **财务中心**：钱包、应收/应付、订单、对账；闭环后开放。
10. **诊断工具**：网关能力等低频工程页面。

### Supplier

1. **供给概览**。
2. **资源登记与维护**。
3. **凭证与代理**。
4. **分配与履约状态**。
5. **收益与结算**。
6. **审计**。

## 9. 优先级

### P0：避免错误承诺和错误操作

1. 下线或重做旧接入向导，提供 client 可读的真实 onboarding 状态接口和进度页。
2. 将账单、收款订单、支付设置、供给管理按成熟度标注或 feature flag 隐藏，避免把估算/骨架说成正式闭环。
3. 决策是否允许 client 查看上游 Key 明文；若统一余额和防绕过优先，则默认关闭导出能力。
4. 修复 supplier 凭证类型、admin 用户选择等前后端权限错配。

### P1：把已实现闭环表达清楚

1. 重构 client 首页、接入进度、服务质量与路由三条主路径。
2. 将 admin 运维中心从只读看板补成可筛选、可钻取、可重试、可人工恢复的操作台。
3. 拆分上游编排，并把 Delivery Key 合入 Channel 的交付准备度。
4. 将上游账号、旧监控开关、旧审批降到自有账号高级模式。

### P2：建立下一阶段新业务

1. 建可信资金账本、价格版本、预授权/冻结、扣款、退款/冲正、余额门禁、上游成本对账和告警，再开放钱包与支付页面。
2. 将 supplier Offer 打通到实际 Channel/Key/部署/消耗和应付结算，再正式开放供应商经营页面。
3. 完善通知投递健康、审计业务化筛选和开发者诊断区。
