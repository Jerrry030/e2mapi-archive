## 3. 计费模型：最需要小心的部分

**这是本轮最微妙的改动，改动前务必读懂，否则很容易做出静默少收或透支失控。**

当前语义（对齐 sub2api 的"允许透支"，但边界更严）：

1. **预扣（reserve）** = `min(上游 MaxRequestMicros, 钱包可用余额)`。
   预扣是上限不是门槛：余额 0.3 元也能发请求（预扣 0.3）。
   **仅当可用余额 ≤ 0 时拒绝**（402）。预扣**不会**制造欠款。
2. **结算（settle）** = 按真实 token × 快照单价收费，**允许超过预扣额**，
   超出部分从可用余额扣；不够则余额转负 = **欠款**。
3. **欠款** 以负 `available_micros` 表示，任何入账（充值 / 兑换 / 管理员调整）自动抵扣。
   欠款期间余额 ≤ 0 → 无法发起新请求。
4. **管理员调整不能制造欠款**（只有结算能），但**贷记必须永远放行**（否则部分还款会被拒——这是修过的 bug）。

配套的数据库变更（缺一不可，少一条就会静默回落到保守结算）：

| 迁移 | 移除的约束 |
|---|---|
| 0081 | `wallet_accounts_available_micros_check`（`available_micros >= 0`） |
| 0082 | `wallet_reservations_check`、`supply_usage_records_check`（均为 `settled_micros <= reserved_micros`） |

两个降级迁移都会在存在欠款/超额结算时 **RAISE EXCEPTION 拒绝执行**，不静默改写客户余额。
`wallet_overdraft_migration_test.go` 锁住这三条约束不会回潮。

## 4. 不变量清单（改动时不要破坏）

- 双分录账本必须平账：结算超出预扣时，借方拆成 `user_reserved` + `user_available` 两笔；
  数据库有 deferred trigger `e2m_assert_wallet_journal_balance` 会校验 `借方 = 贷方 = journal.amount`。
- 上游售价只有一个来源：基准价目表 × 汇率 × 分组倍率。表单已不再提交价格；
  未配置汇率时创建上游必须 **400 拒绝**（不能生成零价上游）。
- 上游标签中 `e2m.model_mapping` 由表单管理，其余标签（含 `e2m.error_cooldown_rules`）
  **必须透传保留**——控制台已无编辑器，重建标签会静默抹掉数据面仍在用的配置。
- 商业化闭环整体受 `E2M_ENABLE_PAYMENTS` 门禁，关闭时**在认证之前** 404 `feature_disabled`，
  且该开关同时覆盖兑换码域（发卡 + 用户兑换）。
- Connector 边界不变：支付、兑换、定价、计费全是 Core 原生能力，不经 Connector。

## 5. 下一步（按优先级）

### P0 — 补真库计费测试（本轮暴露的最大盲区）

内存存储没有任何数据库约束，因此**结算相关的单元测试全绿也不代表真库能跑通**。
本轮 `87844d7` 就是这样出的错：允许负余额后单测全过，真库却因两条 `settled <= reserved`
约束拒绝了每一次超额结算，静默回落到保守结算——正是这轮要消灭的少收行为，直到端到端跑真库才发现。

需要做的：在 `internal/store/postgres_*_test.go` 既有 `E2M_TEST_POSTGRES_DSN` 跳过模式下，
新增一组**真库结算测试**，至少覆盖：

- 结算额 > 预扣额 → 余额转负，账本平账，`settled_micros > reserved_micros` 能写入
- 欠款状态下预扣被拒
- 部分贷记降低欠款、贷记永远放行
- 管理员借记不能制造欠款
- 释放（release）路径的账本平衡

并考虑把这组测试接进 CI（`make ci` 目前不带 DSN，需要起一个 postgres service）。
