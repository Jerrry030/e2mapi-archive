# 个体账号定位校正评估

更新时间：2026-07-09

## 校正后的产品定位

E2M 当前面向个体用户，不按组织、团队、多岗位协作或多级分销来设计。一个自然用户使用一个邮箱注册，账号自身就是资源归属边界；实例、凭证、通知、审计、账单等资源都直接归属于这个账号 ID。

原先考虑过短期复用 `tenant_id` 作为内部资源命名空间和隔离键，但该做法会把错误模型继续留在系统核心。当前项目仍处初期，应优先改成以 `users.id` / `user_id` 为核心的个体账号隔离模型。

## 核心判断

| 项目 | 判断 |
| --- | --- |
| 邮箱 | 产品层面的登录身份，也是用户感知上的资源归属主体。 |
| 资源归属 | 后端不再需要独立租户表或工作区承载个体隔离，直接以 `users.id` / `user_id` 作为资源归属主键。 |
| 账号编号 | 采用自增数字 `users.id`，不保留随机字符串账号 ID 或展示层伪编号；真实资源隔离键就是该数字编号。 |
| 注册页团队/站点字段 | 在个体模型下不应让用户手动填写，也不再自动创建租户/工作区。注册只创建用户账号。 |
| 租户概念 | 应从产品、前端、接口、数据库主路径和迁移脚本中移除；新库直接初始化为个体账号模型，不再保留旧租户模型升级兼容。 |
| 多角色 | 不应表达成组织角色或多人权限；如仍保留，应表达为账号能力/使用模式，例如“托管能力”“供给能力”。 |
| 审批 | 不应表达成上下级审批；应表达为本人二次确认、高风险操作确认或待确认操作。 |

| 范围 | 原问题 | 当前处理 |

| 注册接口 | `AuthRegisterRequest.TenantName` 必填，后端校验 `tenant_name is required`。 | 已删除 `tenant_name`；注册只创建 `users` 记录。 |

| 租户页面 | 控制台有“租户”页面和新增组织流程。 | 已删除租户页面和 `/tenants` 路由；平台管理员通过“用户管理”管理账号。 |

| 审批中心 | L2/L3 动作“需人工批准”“审批中心”。 | 后续环节继续评估是否改为“高风险确认 / 待确认操作”。 |

| 多空间残留 | 文档和少量界面文案仍可能使用“资源空间 / 工作区 / 租户边界”等说法，让人误解为单账号下还有第二层空间。 | 已改为“账号 ID / user_id 直接归属”；迁移脚本也已清理旧租户兼容逻辑。若本地已有旧库，直接重置数据库重新初始化。 |

## 推荐调整方案

### 已执行方案：直接切到用户隔离模型

1. 删除注册链路里的 `tenant_name`。
2. 删除 `tenants` 作为运行时资源归属容器的产品模型。
3. 将当前所有站长侧资源的 `tenant_id` 改为 `user_id`，直接指向 `users.id`。
4. 将供给相关字段从 `supplier_id` / `tenant_id` 调整为 `supplier_user_id` / `owner_user_id`。
5. 将审计、通知、账单、审批、连接器、实例、路由计划、凭证命名空间全部归属到 `user_id`。
6. 前端删除“租户”菜单和普通流程中的租户选择器；平台管理员按账号筛选。
7. RBAC 从“用户角色 + 租户”收敛为“当前用户本人资源 + 平台管理员全局管理”。

### 本次账号编号调整

- `users.id` 已改为数字自增编号，注册后自然得到 `1`、`2`、`3` 这样的账号编号。
- 所有业务资源归属字段继续直接指向账号编号：`user_id` / `supplier_user_id`。
- 控制台侧 `AuthUser.id`、筛选参数、表单中的用户选择值已改为 number，避免前后端类型不一致。
- 迁移层不再提供旧字符串用户 ID / 旧租户模型的自动升级路径；当前雏形阶段以重新初始化数据库为准，初始化后直接得到数字账号 ID 和 `user_id` 归属字段。

## sub2api 用户隔离参考

对 `Wei-Shaw/sub2api` 的源码评估结论：

1. sub2api 的用户主体是 `users` 表，`id BIGSERIAL PRIMARY KEY`，`email UNIQUE`。
2. JWT claims 中携带 `user_id`、`email`、`role`，请求进入后通过 `user_id` 重新读取用户。
3. 用户侧资源用 `user_id` 做归属，例如 `api_keys.user_id`、`usage_logs.user_id`、`user_subscriptions.user_id`。
4. 管理员侧资源如上游账号池 `accounts` 是全局资源，不按普通用户隔离。
5. 因此 sub2api 是“用户 ID 做资源隔离，邮箱做登录唯一标识和展示标识”，不是组织/租户模型。

这与 E2M 的个体账号定位更匹配。E2M 应直接借鉴该思路：邮箱作为唯一登录标识，`users.id` 作为资源隔离主键。不要继续复用 `tenant_id`，否则后续所有实例、凭证、审计、账单、通知和供给逻辑都会继续携带错误抽象。
